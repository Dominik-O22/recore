What it does now

recore-corpus compare and recore-decompile params --against print each total that got worse as a line, and exit 3 when that is all they found wrong:

Worse: corpus-thumb/signatures returns a value or not right 4089 -> 3858 (-231)

A description names the loss with that line at the start of a line of its own, and the reason after it. A real one, from the dry run below:

Worse: corpus-thumb/signatures returns a value or not right 4089 -> 3858 (-231) the base is the head of feat/returns-from-callers, which this branch lacks

  • check.sh collects the losses and holds them to the Worse: lines of RECORE_WORSE_ACCEPTED with a new recore-corpus losses. It prints each loss as accepted or not named, and each line that names nothing of the run as not lost, unread or hidden. A loss no line names fails the run, and so does any line starting Worse: that is not a loss line with a reason, Worse: none too.

  • A line is an upper bound. It accepts a loss of its run and count as large as it names or smaller, so the totals may differ from the run's and the fall may be smaller. A larger fall is not named, printed as the line to write. A line whose loss did not happen prints as not lost and fails nothing.

  • With each signature loss, the run prints how many functions the base and the head left out for a timeout or after a lost worker. It is no gate, since it moves with the load, but it shows whether a slower decompiler is behind an accepted loss.

  • A line counts only where GitHub shows it. Nothing counts inside an HTML comment (also one never closed, which hides the rest of the page), a processing instruction, a declaration, CDATA, a tag's attributes, the content of an element such as <video> or <rp>, or the title of a link reference definition. I checked each against GitHub's own renderer. A <details> block counts: it folds, and a click shows it. The rule errs toward hiding, so a line it hides wrongly fails the run as not named and prints as hidden, never the other way.

  • land.sh gives the run the description as RECORE_WORSE_ACCEPTED. A pull request with a Worse: line never rides a train, since a train's one run cannot say whose loss it was.

  • Editing a description moves no head. So before it merges, land.sh reads the description again and turns the pull request away when its Worse: lines differ from those the check saw.

  • The merge commit keeps its subject and records what the run accepted, as the run measured it, so git log on main keeps it whatever the description says later. Built by land.sh's own extraction from the log of the dry run with all three lines named:

    Merge pull request #218 from Dominik-O22/gate/worse-line

No line accepts a binary that lost its analysis, a decompiler that fails or crashes on more functions, the tests, the instruction budget (Budget:), or time and memory (--accept-cost). CI has no corpora, so nothing checks a line against a run before the landing does. Lines added before the check and seen by nobody are for review: the reviewer of a pull request reads its Worse: lines.

Review

A review of the first version found that a Worse: line inside an HTML comment accepted a loss with nothing on the page. It also found that the description was read once and never pinned, that exact matching would fail honest landings because signature counts move with timeouts, and that a slower decompiler could pass its timeouts off as accepted knock-ons. Smaller findings covered comments that could @mention people or stop the queue, a .trim() no test held, and the status text on the lowered-budget path. Each is fixed as above, and each has a test that failed before its fix: the Rust tests in crates/corpus/src/losses.rs and params.rs, and the new land.test.sh cases.
