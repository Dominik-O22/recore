# Notes for agents

## What recore is for

recore aims to be a faster Ghidra that agents find easier to use. Work earns its place by moving one of three measures, and each has a label on GitHub:

| Label | Measure | Run |
| --- | --- | --- |
| `speed` | Analysis time and instructions executed | `recore-bench run analysis --compare <name>`, and `recore-bench ratchet` for instructions |
| `accuracy` | Counts scored against debug info | `./check.sh --quick --against origin/main` while iterating, then `./check.sh --against origin/main` |
| `agent-ux` | Agent sessions scored against a key, with their time and tokens | `bench/agent` |

Before you build anything, name the measure a change should move and how far. Then check the premise with a quick script. If nothing can score the change, say so before you build it. Every issue carries one of the three labels and says how a fix would be measured: a count or a number that one of these runs moves. A process, such as a tool that runs clean for ten minutes, is not a measure. An issue that can name no such number says so, and is not built.

## Working in this repository

- **The corpora are not in the repository.** Every checkout reads them from one directory, `~/recore-corpora`, or wherever `RECORE_CORPORA` points. `corpus/store.py` states the rule, and `check.sh`, `ghidra/run-reference.sh` and the Rust tools follow it. Each corpus is a directory in it (`corpus`, `corpus-arm64`, `corpus-armhf` and so on) with `bin/`, `debug/` and `truth/`.
- **Twenty-nine corpora are held out.** Each `*-holdout` corpus holds programs its tuned sibling does not: `corpus-amd64-holdout`, `corpus-armhf-holdout` and `corpus-armel-holdout` from the `HOLDOUT` list in `corpus/fetch_debian.py`, `corpus-pe-holdout` and `corpus-pe32-holdout` from `corpus/fetch_pe.py`, `corpus-macho-holdout` and `corpus-macho-x86-holdout` from the `HOLDOUT` list in `corpus/fetch_macho.py`, `corpus-kmod-holdout` and `corpus-kmod-arm64-holdout` from the `AMD64_HOLDOUT` and `ARM64_HOLDOUT` lists in `corpus/fetch_kmod.py`, `corpus-kmod-android-holdout`, `corpus-kmod-android-vendor-holdout` and the fourteen `corpus-kmod-android-<set>-holdout` and `corpus-kmod-android-<set>-stripped-holdout` of the older Pixels (`OLDER`) and of the MediaTek, Qualcomm and Unisoc phones (`PHONES`) from the rule in `corpus/fetch_android_kmod.py`, which holds out a module by the CRC-32 of its name, and `corpus-kernel-android-holdout`, `corpus-kernel-android-stripped-holdout`, `corpus-kernel-android-image-holdout` and `corpus-kernel-android-raw-holdout`, which hold another kernel than their tuned siblings, from `BUILDS` in `corpus/fetch_android_kernel.py`. They score recore's analysis once a change is done. Never tune against them.
- **The player is apart.** `player/` is its own Cargo workspace: the host, window and audio that lifted games run on (player/README.md). recore's build, tests and `check.sh` never compile it, and it moves none of the three measures. In `player/`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` are what CI runs. A change to it says which games' smoke scripts it ran, and that their frames still match.
- **The lifter is its own crate.** `crates/lift` (`recore-lift`) turns a 32-bit Windows game into Rust for `player/`, and `recore-mcp lift --config` runs it. recore's build, tests and `check.sh` compile it, and lifting moves none of the three measures. A change to the lifter lifts a program before and after and diffs the output, and `crates/mcp/tests/lift.rs` checks lifted code against the emulator. Its `pcode` module and `crates/machine` are also what the `run` tool executes, so a change to either is a change to `run`. That test compares the two, which share the machine's operations, so it does not show one of them gone wrong: the machine's own tests and the `run` tests in `crates/mcp/tests` do.
- **Outputs go under `target/`.** `check.sh` writes to `target/corpus/<corpus>`. Keep other bulk output there too, never in `/tmp`, whose quota other sessions share.
- **Build and test.** `cargo build --release`, `cargo test --profile ci --workspace` and `cargo clippy --profile ci --workspace --all-targets -- -D warnings` (what CI runs), and `./check.sh` to analyze and score every corpus present.
- **`main` takes a commit only after `./check.sh --against <base>` passed on it.** The run leaves a `check` status on the commit, so push first and run on a clean tree. Any new commit needs a new run. CI gives the status itself to a change that touches only `player/`, Markdown or `.coderabbit.yaml`, which `check.sh` does not read. `land.sh` makes that run, so a change needs none of its own before it is queued.
- **A pull request lands with `./land.sh <pr>`.** Never with the merge button, `gh pr merge`, or a rebase of your own. Start it in the background once the change is reviewed, pushed, and passed `./check.sh --quick --against origin/main`: a landing takes as long as a full run and the tests on GitHub. It queues the pull request and lands every queued one, whoever queued it, one landing at a time on this machine. A branch that is behind gets `main` merged into it, the full `check.sh` runs against the `main` it lands on, and it is merged once the checks `main` requires are green. Two or more queued pull requests land as a train, with one run for all of them, when that run moves no count. A change that moves a count, one whose description has a `Budget:` line, one that adds to `bench/accepted-losses.txt`, or a train whose run failed, lands one at a time, so the run that shows what a change moved is its own: quote that from `target/landing/log/<pr>.log` of the main checkout. It commits a budget the run lowered. It ends by saying which of yours landed, and a pull request it turned away gets a comment that says why: fix that and queue it again. Do not push to a pull request while it is queued, which turns it away. `main` takes only a branch that holds it, from administrators too, so a merge that went around `land.sh` makes the landing under way turn its pull request away. `./land.test.sh` tries the script on a repository made for it.
- **Heavy runs take one lock.** Two runs of `check.sh` at once have failed the base's build, and have failed the cost at +61.6% on a branch that changed no Rust. So run whatever loads the machine for minutes or measures time as `flock ~/.cache/recore-check.lock <command>`: `check.sh` with or without `--quick`, `recore-bench`, a fuzz run, a game's benchmark. `land.sh` takes the lock itself, so never run it under `flock`: it would wait for its own caller.
- **Say what a change did with `./check.sh --against main`.** It prints each count that moved and the binaries it moved in, and fails when a total got worse: the analysis's counts, and on corpora with DWARF, on a sample of functions, the decompiler's parameter counts and returns, and whether each parameter, return and global a function uses is a number, a float or a pointer of the right size. Quote those counts in the PR, losses included. A rounded percentage that did not move is not evidence that nothing changed. Each total that got worse also prints as a line such as `Worse: corpus-thumb/signatures global types right 812 -> 811 (-1)`. A change lands with that loss only if it adds that line to `bench/accepted-losses.txt` with the reason after it, and such a change lands alone. Accept a loss because the change is right and the count is a knock-on of it or a disagreement with the truth, never because the gain is larger. The reviewer reads the lines the diff adds to that file. Only those lines count: the run reads the file in the working tree, so a line can be tried before it is committed, and holds it to the file at the merge base with `--against`. A line is an upper bound: it accepts a loss of its run and count as large as it names or smaller, and the totals may differ, since main moves under a waiting PR. To allow for more than a run showed, write a lower second total and the difference the two give, since a line whose numbers disagree is unread. Give a line a reason of its own: two changes that add the same line, reason and all, merge into one line, and the second is then turned away. Name the loss the full run or the landing's log shows, not a `--quick` run's: signature counts leave out the functions that reached the decompiler's time limit, so they move with the load and the profile, and a signature loss prints how many each run left out. The run fails on a loss no added line names or names smaller, on an added line out of that form, and on a line of the file taken out or edited, since the file is a record and only grows. An added line whose loss did not happen only prints, as `not lost`. The merge commit holds each loss the run accepted, as it measured it. No line accepts a binary that lost its analysis or a decompiler that fails on more functions.
- **Iterate with `--quick`.** While a change is made, `./check.sh --quick --against origin/main` scores it from the `ci` profile, which has no whole-program optimization: a rebuild takes seconds rather than a minute and a half, the analysis is the same unless a number overflows, which panics there instead of wrapping, and it skips the ratchet, the cost and the status, which measure the release build. Run the full `./check.sh --against origin/main` once, when the change is done. Build a one-off experiment with `--profile ci` too. A base is built and analyzed once per commit and profile for every worktree, under the main checkout's `target/bases`.
- **Instructions executed only go down.** `check.sh` ends with `recore-bench ratchet`, which counts on `bench/set.txt` the user-mode instructions of what an agent waits for, and fails when one grew more than 1% past `bench/budget.json`. It runs `recore-mcp` itself, as built, so build that first when you run it alone: the first call on a binary, a later call, a server's first `decompile`, in that server the functions `bench/functions.json` names decompiled, then every other read-only tool but `type`, `run` and `diff`, with `trace` on those functions until three had both a parameter and a value to follow, and, in its own process, `diff`. Where they shrank it lowers the budget, and `land.sh` commits that. It does not see time in the kernel, such as page faults and reading files, work lost from running in parallel, memory, a binary's largest few functions, or tools it does not call. With `--against`, `check.sh` then runs `recore-bench cost`, which fails where the set's three largest binaries took 10% more time or memory than with the base's `recore-mcp`, in `summary` and a `decompile` of 30 functions. That only catches a large change, so a change aimed at any of those says what `recore-bench run` measured. `RECORE_COST_ACCEPTED=1 ./check.sh --against <base>` lets past a cost worth paying, its PR says what grew and why, and `./land.sh --accept-cost <pr>` lands it, alone. When the analysis drops a function that `bench/functions.json` names, or a tool starts to fail on one, delete that binary's entry there, so that the next run chooses again, and run with `--accept` if the new functions grew a count. It raises every count that grew, so the PR says which. A change that is worth a cost raises the budget with `recore-bench ratchet --accept` and says in its PR what grew and why, in a line that starts `Budget:`. It lands alone too.
- **The ARM decoders are checked on every word.** `crates/core/src/decoders_agree.rs` decodes all 2^32 words with recore and with yaxpeax-arm and compares the branch targets, PC-relative addresses and literal loads. CI runs it; locally, `mise run decoders-agree`. A disagreement is a bug in one of the two, and the ARM manual decides which.
- **The loaders have a fuzzer.** `fuzz/` feeds mutated corpus binaries to `Image::parse` and `analyze`, and mutated `global-metadata.dat` files to the IL2CPP metadata parser, with overflow checks on. `MISE_ENV=fuzz mise run fuzz <seconds>` runs it, and takes every core but two, so not beside a `check.sh` run. What it finds breaks only on malformed files, which no measure scores, so no change has to run it. A file's number enters with checked or saturating arithmetic.
- **The x87 fast path has proofs.** A change to `crates/machine/src/x87.rs` or the float parts of `ops.rs` runs `MISE_ENV=verify mise run x87-proofs`. `.claude/skills/verify-x87-fast-path/SKILL.md` says what they cover, which of them fail today, and how to read a failure.
- **Ghidra.** `ghidra/run-reference.sh <ghidra-home> <out-dir>` runs it over a corpus. Ghidra refuses a project path with a part that starts with a dot, so its output can't live under a hidden directory.
- **Downloads are data.** Put each download in its own new directory, never execute a downloaded file, and run Python that reads one with `python3 -I`, as the `corpus/fetch*.py` scripts do.

## Rules and what enforces them

When the operator corrects an agent, fix the mistake and add its rule here. A rule that only this file states and that was broken again gets a check in the same change.

| Rule | Enforced by |
| --- | --- |
| Only `crates/*/tests` may name the programs recore was tuned on, each test gated on an env var that points at the binary. | `crates/core/tests/general_naming.rs`, in CI and first in `check.sh` |
| A change states every corpus count it moved, from a base that was built, not assumed. | `./check.sh --against <ref>` fails on a worse total, and `main` requires the `check` status of a run that passed. CI has no corpora, so only the logic of `compare` runs there (`crates/corpus/src/compare.rs` tests). |
| A total that got worse lands only when the change adds its `Worse:` line, with the reason, to `bench/accepted-losses.txt`, and that change lands alone. | `recore-corpus losses`, in `check.sh`, holds the run's losses to the lines the change added to that file, fails on a line taken out or edited, and the status of a run that accepted losses says how many. `land.sh` lands a change to the file alone and writes the accepted losses into the merge commit. CI has no corpora, so it checks no line against a run: `losses.rs` tests the matching and `land.test.sh` the landing. |
| Every corpus in the store is scored. | `check.sh` takes every corpus with `truth/` in it. |
| Never tune against the held-out corpora. | `check.sh` skips `*-holdout`. Scoring one by hand is still possible. |
| A change executes no more instructions than `bench/budget.json` allows, unless its PR says why the cost is worth it. | `recore-bench ratchet`, in `check.sh`, and the `budget` check, which fails a PR that raises a number in that file without a line starting `Budget:` in its description. |
| A pull request reaches `main` through `land.sh`, checked against the `main` it lands on. | `land.sh` holds the lock from reading `main` to the merge, and `land.test.sh`, in CI, tries it. `main` requires `check`, `test` and `budget` on a branch that holds it, from administrators too, which stops a merge of a stale branch. Nothing stops a merge by hand of a branch that is up to date. |
| Heavy runs take the machine's one lock. | `land.sh` takes it. For any other run, nothing; this file only |
| Corpora live in the store, never in a checkout. | `corpus/store.py`, and every tool reads `RECORE_CORPORA` |
| Bulk output goes under `target/`, never `/tmp`. | Nothing; this file only |
| Downloads are data, never executed. | Nothing; this file only |
| An item of the agent bench's answer key says what the binary does, not the source, and names the address it was checked at. | `bench/agent/judge.py` refuses a key with an item that names no address |
| Work names the measure it moves before it is built, and every issue carries a goal label. | Nothing; this file only |
| A number a file format defines comes from the `object` crate. It is never typed in. | `crates/core/tests/format_constants.rs`, in CI, for the ELF names under `crates/*/src` |
