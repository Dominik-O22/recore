# Answer key: an Android kernel and three of its modules

One point per item. An item passes when the report states it, and a report that asserts something this key calls false fails the item that covers it. An error number passes as the negative number, in decimal or hex, or as its name: -22, -0x16 or -EINVAL.

The inputs come from two GKI builds on ci.android.com, which `fetch.py` pins by sha256. `Image` is the kernel of build 16924931 of android13-5.15, and its addresses are the kernel's own, from 0xffffffc008000000. `gzvm.ko`, `zram.ko` and `rfkill.ko` are modules of build 16958505 of android14-6.1, stripped with `llvm-strip --strip-unneeded`. recore lays a module's sections out from 0xffff800000000000 in the order of the file, and the addresses below are those; each derivation also gives the section offset, which holds for any tool. Names come from the debug files, for whoever checks the key. The agent sees none of them, but for the names `Image`'s own symbol table holds and the global symbols a stripped module keeps.

Each task ends with how its key was derived, so it can be checked again. `derive.sh` writes what the derivations read to `target/agent/android/derive`: each module's disassembly with its relocations (`<module>.dis`) and its strings, the kernel functions named below, and the callers `callers.py` finds. `words.py` reads the kernel's tables.

## Task A: gzvm's ioctl interface

- **A1.** The driver registers a misc device named "gzvm" (its record at 0xffff800000006688, registered at 0xffff800000001d7c by the probe 0xffff800000001d58). Its file operations at 0xffff800000006088 hold the ioctl handler 0xffff800000001de8 at +0x50 (0xffff8000000060d8). The handler's address is needed.
- **A2.** The handler handles two commands. 0x9201 passes its argument, the VM's type, to the function that makes a VM (0xffff800000002048) and returns what that returns, a file descriptor. 0x9203 passes its argument, a pointer to an 8-byte extension number in user memory, to the extension query (0xffff800000001bec) and returns its answer. Needed: 0x9201 makes a VM and returns a file descriptor, and 0x9203 queries an extension, with its argument a pointer into user memory.
- **A3.** A command it does not handle returns -25, -ENOTTY (0xffff800000001e30). 0x9203 with an argument of 0 returns -22, -EINVAL (0xffff800000001e38), without querying. Both are needed.
- **A4.** The VM is an anonymous inode named "gzvm-vm", whose file operations at 0xffff800000006198 hold the handler 0xffff8000000023fc at +0x50. It handles nine commands: 0x9203, 0x9241, 0x40089261, 0xc03092e0 (which a signed listing shows as -0x3fcf6d20), 0x40209246, 0x40209276, 0x40409279, 0x403092a3 and 0x401092ff, and returns -25 for any other. All nine numbers are needed; what each does is not.

Derivation. In `derive/gzvm.dis`, `gzvm_drv_probe` (.text+0x1b8) registers `gzvm_dev` (.data+0xf8), whose `fops` is `gzvm_chardev_ops` (.rodata+0x1c0); `.rela.rodata` in `derive/gzvm.relocs` puts `gzvm_dev_ioctl` (.text+0x248) at its +0x50, `unlocked_ioctl`. `gzvm_dev_ioctl` compares with 0x9203 and 0x9201 and returns -0x19 for the rest (.text+0x290) and -0x16 for 0x9203 with x2 zero (.text+0x27c, .text+0x298). `gzvm_dev_ioctl_check_extension` copies 8 bytes from the argument. `gzvm_dev_ioctl_create_vm` (.text+0x4a8) ends in `anon_inode_getfd("gzvm-vm", &gzvm_vm_fops, ...)`, and `gzvm_vm_fops` (.rodata+0x2d0) holds `gzvm_vm_ioctl` (.text+0x85c) at +0x50. The nine commands are the constants `gzvm_vm_ioctl` builds with `mov`/`movk` and compares with w1 for equality; 0x9240, 0x401092fe and 0x40209275 are bounds of its search and not commands.

## Task B: a guest memory region, from user space to the hypervisor

- **B1.** Command 0x40209246 reads 0x20 bytes from the caller (0xffff80000000274c). The first 32-bit word is the slot, which must be below 10 (0xffff800000002798); a slot of 10 or more returns -6, -ENXIO. Needed: 0x20 bytes, the slot below 10, and -6 otherwise.
- **B2.** It looks up the mapping that holds the user address at +0x18 of what the caller gave, in the process that made the VM (`mtree_load` on the mm at +0x40 of the VM's record, 0xffff800000002b98): no mapping returns -14, -EFAULT. The mapping's size must equal the size at +0x10 (0xffff800000002bac), else -22, -EINVAL. Both checks are needed.
- **B3.** The guest physical address, at +0x8 of what the caller gave, is stored shifted right by 12, as a page frame number, at +0x48 + 0x28 × slot of the VM's record (0xffff800000002be0): the slots are 0x28 bytes each from +0x48. The offset and the shift are needed.
- **B4.** For the hypervisor it fills a 0x2000-byte buffer with the slot at +0x0, the number of pages at +0x8 and the guest physical address, the frame shifted back, at +0x10 (0xffff800000002c54). 0xffff800000004dd4 then makes an HVC with 0xbb001004 in x0, the VM's 16-bit id from +0x280 of its record in x1, 0x2000 in x2 and the buffer's physical address in x3 (0xffff800000004e24). The call number, x3 holding the buffer and the address at +0x10 of it are needed.

Derivation. In `derive/gzvm.dis`, the case of `gzvm_vm_ioctl` for 0x40209246 copies 0x20 bytes (.text+0xbac) and inlines `gzvm_vm_ioctl_set_memory_region`: `cmp w20, #0x9` (.text+0xbf8) with -6 in x21 when it fails, `mtree_load(mm, userspace_addr)` (.text+0xff8) with -14 in x21 for no mapping, `vm_end - vm_start` against `memory_size` (.text+0x100c) with -22 at .text+0x1120, and the stores into the slot at `x19 + 0x28 * slot + 0x48` from .text+0x103c on, the frame `guest_phys_addr >> 12` at .text+0x1040. The inlined `register_memslot_addr_range` allocates 0x2000 bytes (.text+0x1070), writes the slot, the pages and `base_gfn << 12` at +0x0, +0x8 and +0x10 (.text+0x1090 to .text+0x10b4), and calls `gzvm_arch_set_memregion(vm_id, 0x2000, __pa(region))` (.text+0x10d0), which passes 0xbb001004 and its three arguments to `__arm_smccc_hvc` (.text+0x3234 to .text+0x3284).

## Task C: what zram registers

- **C1.** The block device operations table is at 0xffff8000000048d8, and each new disk gets it (0xffff800000001e74). It fills four function slots and the owner: +0x0 with 0xffff800000002608 (submit_bio), +0x10 with 0xffff8000000029a0 (open), +0x20 with 0xffff8000000029f8 (rw_page), +0x60 with 0xffff800000002b68 (swap_slot_free_notify), and +0x80 with the module. The four functions with their offsets are needed; the slots' names are not.
- **C2.** The function that creates a device is 0xffff800000001da4, which module init (0xffff8000000047b4) and the show function of the class attribute hot_add (0xffff800000002050) call. It allocates 0x168 bytes, zeroed (flags 0xdc0), for the device's record (0xffff800000001dc8). The function's address and the size are needed.
- **C3.** Its checks: a failed allocation returns -12; it takes an id from an IDR (0xffff800000001dec), and a negative id frees the record and is returned; a disk it cannot allocate (0xffff800000001e24) prints "Error allocating disk structure for device %d", removes the id, frees the record and returns -12, -ENOMEM (0xffff800000001fa8); a failed `device_add_disk` puts the disk, removes the id, frees the record and returns that error. The -12 for the disk is needed.
- **C4.** A new device's compression algorithm is "lzo-rle", copied into +0xe0 of its record, 8 bytes at most, once the disk is added (0xffff800000001fc0). "lzo-rle" is needed; the offset is not.

Derivation. In `derive/zram.dis`, `zram_add` (.text+0x4f4) calls `kmalloc_trace(..., 0xdc0, 0x168)` (.text+0x518), `idr_alloc` (.text+0x53c), `__blk_alloc_disk` (.text+0x56c) with the error path at .text+0x6e8, stores `&zram_devops` (.rodata+0x38) at +0x48 of the disk, `fops` (.text+0x5c4), and calls `strscpy(zram->compressor, "lzo-rle", 8)` (.text+0x710); the strings are at the offsets of `.rodata.str1.1` the relocations name, in `derive/zram.str`. `.rela.rodata` in `derive/zram.relocs` puts `.text+0xd58` (`zram_submit_bio`), `.text+0x10f0` (`zram_open`), `.text+0x1148` (`zram_rw_page`), `.text+0x12b8` (`zram_slot_free_notify`) and `__this_module` at .rodata+0x38, +0x48, +0x58, +0x98 and +0xb8: slots +0x0, +0x10, +0x20, +0x60 and +0x80 of `block_device_operations`. `zram_add`'s callers are `init_module` and `hot_add_show` (.text+0x7a0).

## Task D: rfkill's write, and how long it reads

- **D1.** The write handler is 0xffff800000002f04, the only caller of `copy_from_user`. A buffer shorter than 7 bytes returns -22, -EINVAL, before anything is read (0xffff800000002f24): a 5-byte write returns -22. The handler's address and -22 for a 5-byte write are needed.
- **D2.** It reads the smaller of the length, a limit and 9 bytes into a zeroed 9-byte event (0xffff800000002f3c, 0xffff800000002f58). The limit is the byte at +0x69 of the open file's private record, which open (0xffff800000003414) sets to 8 (0xffff80000000346c). So a 100-byte write on a fresh descriptor reads 8 bytes and returns 8 when the event is accepted. Reading 8, returning 8 and the limit's offset, +0x69, are needed.
- **D3.** The limit is changed by the ioctl handler 0xffff800000003284. It takes only commands of type 'R' (0x52) and number 2, and checks no other bits of the command (0xffff8000000032a0); any other command returns -38, -ENOSYS. It reads a 4-byte value through the argument and stores its low byte at +0x69 (0xffff8000000033d8) when the value is 8 to 255; any other value returns -22. The ioctl's number (type 'R' and number 2, or 0x5202 in its low 16 bits) and the range 8 to 255 are needed. This build's handler takes no other ioctl: a report that says it handles another, such as number 1, RFKILL_IOCTL_NOINPUT, fails. Even at 255 a write reads at most 9 bytes.
- **D4.** The event is accepted when the type, the byte at +4, is at most 8 (0xffff800000003038), and the operation, the byte at +5, is 3, which sets every device of that type, or all devices for type 0, or 2, which sets the device whose index is the 32-bit word at +0 and, for a type other than 0, whose type matches (0xffff800000003058, 0xffff800000003060). Any other type or operation returns -22. It does this holding a global mutex. The two bytes and their limits are needed.

Derivation. In `derive/rfkill.dis`, `rfkill_fop_write` (.text+0x163c) compares the length with 7 (.text+0x165c), takes `data->max_size` from +0x69 of `file->private_data` (.text+0x1674), clamps to 9 (.text+0x1690), copies (.text+0x1724), compares the type with 8 (.text+0x1770) and the operation with 3 and 2 (.text+0x1790, .text+0x1798) under `rfkill_global_mutex`, and returns the clamped length when nothing failed. `rfkill_fop_open` (.text+0x1b4c) stores 8 at +0x69 of the 0x70-byte record it allocates. `rfkill_fop_ioctl` (.text+0x19bc) compares `cmd & 0xff00` with 0x5200 and `cmd & 0xff` with 2, and returns -38 otherwise; it reads the value with `get_user` and accepts it when `value - 0x100 >= 0xffffff08` unsigned, which is 8 to 255 (.text+0x1afc). RFKILL_IOCTL_NOINPUT, number 1, is not built in.

## Task E: binder's ioctl in the kernel image

- **E1.** binder's ioctl handler is `binder_ioctl` at 0xffffffc00918f240, named by the image's own symbol table. The address is needed.
- **E2.** 0x40046205 goes through a jump table at 0xffffffc009f725dc, whose entry 0 leads to 0xffffffc00918f36c. It reads 4 bytes from the argument; a failed read returns -22. It stores the value as it is at +0x188 of the process's record (0xffffffc00918f3a0). It makes no check on the value: any 32-bit value, negative ones included, is stored. The 4 bytes, the offset 0x188 and that nothing is checked are needed.
- **E3.** While it stores the value it holds the process's inner lock: `_binder_inner_proc_lock` (0xffffffc009194f30) takes the spin lock at +0x248 of the process's record, and `_binder_inner_proc_unlock` (0xffffffc009195018) releases it after the store (0xffffffc00918f4ec). Naming the inner lock, or a spin lock at +0x248 of the record, passes.
- **E4.** Before it looks at the command, the handler calls `binder_get_thread` (0xffffffc0091944d8) for the calling thread's record, and returns -12, -ENOMEM, when that returns none (0xffffffc00918f3a8). -12 is needed.

Derivation. `derive/binder_ioctl.dis`: `binder_get_thread` at 0xffffffc00918f324 with -12 at 0xffffffc00918f3a8; commands above 0x40046204 index the table at 0xffffffc009f725dc by `cmd - 0x40046205` (0xffffffc00918f340 to 0xffffffc00918f368), and the 4-byte entries, offsets from 0xffffffc00918f35c, send index 0 to 0xffffffc00918f36c; there `_copy_from_user(&max_threads, ubuf, 4)` with -22 at 0xffffffc00918f640 on failure, `_binder_inner_proc_lock`, `str w8, [x21, #0x188]` and `_binder_inner_proc_unlock` at 0xffffffc00918f4ec. `llvm-objdump -d --start-address=0xffffffc009194f30 --stop-address=0xffffffc009195018 key/vmlinux` shows the lock taken with `casa` on x0 + 0x248.

## Task F: a system call, and callers

- **F1.** `sys_call_table` is at 0xffffffc009f7e8a8, and its entry 434 at 0xffffffc009f7f638 holds 0xffffffc0097741f0, `__arm64_sys_pidfd_open.cfi_jt`: a stub of clang's CFI that branches to `__arm64_sys_pidfd_open` at 0xffffffc00817d1d8, which calls `__se_sys_pidfd_open` at 0xffffffc00817d204 with the pid and the flags. The entry's address and pidfd_open are needed; the stub need not be named.
- **F2.** `__se_sys_pidfd_open` checks, in this order: a pid below 1 returns -22 (0xffffffc00817d220); flags with any bit set but 0x800, O_NONBLOCK, return -22 (0xffffffc00817d22c); no process with that pid, `find_get_pid` returning none, returns -3, -ESRCH (0xffffffc00817d23c). Then it calls `pidfd_create` (0xffffffc00817d4fc). The three checks, their returns and the pid checked before the flags are needed; the source checks the flags first, so a report with the flags first fails.
- **F3.** `binder_proc_dec_tmpref` (0xffffffc009192c40) is called directly by four functions: `binder_ioctl` (0xffffffc00918f96c), `binder_deferred_func` (0xffffffc009190c44), `binder_free_thread` (0xffffffc009193db0) and `binder_transaction` (twice, 0xffffffc0091a30c8 and 0xffffffc0091a356c). All four are needed. A report that names as a direct caller a function with no `bl` to it in this build fails: `binder_deferred_release`, which this build inlines into `binder_deferred_func`, or `binder_thread_dec_tmpref`, which reaches it only through `binder_free_thread`, or `binder_ioctl_get_freezer_info`.

Derivation. `words.py target/agent/android sys_call_table 0xd90` prints `0xffffffc009f7f638: 0xffffffc0097741f0 __arm64_sys_pidfd_open.cfi_jt`, and `llvm-objdump -d --start-address=0xffffffc0097741f0 --stop-address=0xffffffc0097741f8 key/vmlinux` shows `bti c; b __arm64_sys_pidfd_open`. `derive/__arm64_sys_pidfd_open.dis` shows the call to `__se_sys_pidfd_open`; `llvm-objdump -d --start-address=0xffffffc00817d204 --stop-address=0xffffffc00817d308 key/vmlinux` shows the checks at the addresses above. `derive/binder_proc_dec_tmpref.callers`, from `callers.py`, lists the five call sites.
